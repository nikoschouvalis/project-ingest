# Configuration & Workspace

## Overview

Project Ingest uses a workspace directory (`.project-ingest/`) that lives in the project root. This directory contains all configuration, artifacts, templates, and run history.

### Report Template

Teams can provide custom report templates. The default produces:
- Executive summary (2-3 paragraphs)
- Key metrics (findings by severity, by category)
- Top risks
- Recommended next steps
- Progress since last run (if applicable)

## Rulesets

### What Are Rulesets?

Team-provided markdown files that define project-specific standards, conventions, and patterns. These are consumed by scan and analysis commands as additional context.

### Location

`.project-ingest/rulesets/`

### Example Ruleset
React Frontend Standards

Component Patterns

Use functional components exclusively
Props interfaces must be explicitly typed (no any)
Components over 150 lines should be split
Custom hooks for shared logic (no logic in components)
State Management

Zustand for global state
React Query for server state
Local state only for UI-specific concerns
File Structure

One component per file
Co-locate tests: Component.test.tsx next to Component.tsx
Shared components in /components/shared/
Page-specific components in /components/pages/<page>/
Naming

Components: PascalCase
Hooks: camelCase with use prefix
Utils: camelCase
Constants: SCREAMING_SNAKE_CASE
Files: Match the default export name
Testing Requirements

All components must have at least one render test
Custom hooks must have unit tests
Integration tests for user flows
No snapshot tests
Performance

Lazy load routes
Memoize expensive computations
No unnecessary re-renders (React.memo where appropriate)
Images must use next/image or equivalent optimization

## Org-Level Configuration

Teams managing multiple repos can maintain an org-level config that projects inherit from.

### Usage

```bash
ingest:init --from /path/to/org-defaults.md

Behavior
Org config provides defaults for priorities, tooling, behavior, and rulesets
Project-level config can override any field
ingest:init will pre-fill from org config and ask only project-specific questions (boundaries, project name, etc.)
.gitignore Considerations

Teams should decide what to commit vs. ignore:

Recommend committing:

config.md — Team should review and version this
templates/ — Shared across the team
rulesets/ — Shared across the team
manifest.md — Useful for tracking
Consider ignoring (large/transient):

scans/ — Can be regenerated, may be large
analysis/ — Can be regenerated
execution/ — Agent logs, transient
Recommend committing (valuable artifacts):

plan/ — Reviewed and approved by team
tickets/ — May be pushed to Jira, but useful as source of truth
reports/ — Stakeholder deliverables
Teams decide based on their workflow. A suggested .gitignore entry:

# Project Ingest - transient artifacts
.project-ingest/scans/
.project-ingest/analysis/
.project-ingest/execution/
